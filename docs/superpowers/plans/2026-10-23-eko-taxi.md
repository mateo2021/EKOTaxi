# Eko Taxi Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Webowa aplikacja przejazdów „Eko Taxi” (wzorowana na Bolt/Uber) spełniająca 7 wymagań zaliczeniowych: logowanie, preferencje, baza, powiadomienia Discord, czatbot przez Claude Code headless, hosting Vercel, repo GitHub.

**Architecture:** Next.js (App Router) na Vercelu rozmawia z Supabase (Postgres + Auth + Realtime, RLS). Kursy są symulowane — status wyliczany z czasu przy każdym odczycie, zmiany statusu wysyłają webhook Discord. Czatbot to lokalny proces Node (`worker/`) subskrybujący `chat_messages` i wywołujący `claude -p`.

**Tech Stack:** Next.js (create-next-app@latest, TypeScript, Tailwind, App Router), `@supabase/supabase-js` + `@supabase/ssr`, `leaflet` + `react-leaflet`, Vitest, Node.js LTS, Claude Code CLI.

**Spec:** `docs/superpowers/specs/2026-10-23-eko-taxi-design.md`

## Global Constraints

- Cały tekst UI po polsku. Nazwa aplikacji: „Eko Taxi”. Żadnych nazw/logotypów Bolt ani Uber.
- Klasy: `economy` | `comfort` | `xl`; mnożniki 1.0 / 1.3 / 1.6.
- Cena: `distance_km = haversine × 1.3`; `price = (5 + 3 × distance_km) × mnożnik`, zaokrąglenie do 1 zł, minimum 10 zł.
- Progi statusu od `created_at`: <5 s `searching`, ≥5 s `accepted`, ≥35 s `in_progress`, ≥95 s `completed`. Polling klienta co 3 s.
- Statusy: `searching` | `accepted` | `in_progress` | `completed` | `cancelled`; anulowanie możliwe tylko w `searching`/`accepted`.
- Worker: timeout `claude` 60 s, kolejka sekwencyjna, heartbeat co 10 s, „online” gdy `last_seen` < 30 s.
- Sekrety nigdy w repo: `.env.local`, `worker/.env` w `.gitignore`; w repo tylko `.env.example`.
- Każde zadanie z UI (6, 7, 8, 9, 10) MUSI wywołać skill `frontend-design:frontend-design` przed pisaniem komponentów. Kierunek wizualny: „eko” — zieleń jako kolor akcentu, czysty mapowy layout jak w aplikacjach przejazdów, motyw jasny i ciemny przez `data-theme` na `<html>`.
- Commit po każdym zadaniu (lub częściej) i od razu `git push origin main` — użytkownik śledzi postęp na GitHubie.
- Komendy uruchamiać w PowerShell lub Bash z katalogu repo; Node instalowany w Zadaniu 0.

## Review Focus

1. **Prompt injection w czatbocie uruchamianym na PC autora** — pytanie użytkownika nie może sprawić, że `claude` wykona komendy/edytuje pliki. Worker: `spawn` bez shella, prompt przez stdin, `--disallowedTools` dla wszystkich narzędzi, cwd = pusty katalog tymczasowy, limit 500 znaków pytania. Test w Zadaniu 10.
2. **Webhook Discord podany przez użytkownika (SSRF)** — serwer może wysyłać tylko na `https://discord.com/api/webhooks/...` lub `https://discordapp.com/api/webhooks/...`. Test w Zadaniu 4, walidacja też w Zadaniu 6.
3. **Odświeżenie strony / powrót po kilku minutach w trakcie kursu** — status musi wynikać z czasu, a nie z kolejnych wywołań; kurs zakończony nie wraca do innego stanu, anulowany zostaje anulowany. Test w Zadaniu 3.
4. **Równoległe odczyty tego samego kursu (dwie karty)** — każda zmiana statusu ma dokładnie jedno powiadomienie (warunkowy UPDATE na `last_notified_status`). Test `shouldNotify` w Zadaniu 3 + kontrola ręczna w Zadaniu 7.
5. **Ten sam punkt startu i celu / brak kierowcy danej klasy** — cena minimalna 10 zł; gdy brak kierowcy klasy, wybór dowolnego. Testy w Zadaniach 3 i 7.
